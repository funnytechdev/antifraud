# Antifraud

Антифрод-сервис, который в реальном времени проверяет карточные операции: по каждой транзакции
из Kafka выносит решение `ALLOW`, `REVIEW` или `BLOCK` и сохраняет его вместе с причинами.

Реальных данных нет, поэтому в проект входит генератор: он создаёт поток обычных покупок и
подмешивает размеченные мошеннические сценарии. Разметка позволяет измерить качество — сколько
мошенничества поймано и сколько честных клиентов задето зря.

> Проект в разработке. Готовы этапы 1 и 2: полный набор правил, настройки без перезапуска,
> защита от повторной доставки и работа при отказе Redis.

## Архитектура

```
[transaction-generator] ──► Kafka: transactions ──► [antifraud-service] ──► Kafka: decisions
          │                                            │        │
          └──► Kafka: transaction-labels             Redis   PostgreSQL
               (разметка для оценки качества)   (состояние   (решения, правила,
                                                   карт,       пороги)
                                                 чёрные списки)
```

| Модуль | Назначение |
|---|---|
| `contracts` | Форматы сообщений Kafka, общие для генератора и сервиса |
| `transaction-generator` | Модель клиентов, карт и магазинов; поток операций с мошенническими сценариями |
| `antifraud-service` | Правила, скоринг, запись решений, REST API |

## Запуск

Нужны Docker и любая JDK 17+ для запуска Gradle. Проект собирается на JDK 25: если её нет,
Gradle скачает её сам.

```bash
docker compose up -d --wait                  # Kafka (KRaft), Redis, PostgreSQL
./gradlew :antifraud-service:bootRun         # сервис на http://localhost:8080
./gradlew :transaction-generator:bootRun     # поток транзакций, 20 операций в секунду
```

Посмотреть решения:

```bash
curl "http://localhost:8080/api/v1/decisions?verdict=BLOCK&limit=5"
curl "http://localhost:8080/api/v1/decisions/{transactionId}"
```

Сервис можно запустить и без Docker Compose — он сам поднимет зависимости в Testcontainers:

```bash
./gradlew :antifraud-service:bootTestRun
```

PostgreSQL из Compose опубликован на порту 5433, чтобы не конфликтовать с локально установленным.
Порты меняются переменными окружения `POSTGRES_PORT`, `REDIS_PORT`, `KAFKA_PORT`.

## Правила

Каждое сработавшее правило добавляет баллы риска. Сумма сравнивается с порогами:
по умолчанию от 40 — `REVIEW`, от 80 — `BLOCK`.

| Правило | Что ловит | Баллы | Как устроено |
|---|---|---|---|
| `VELOCITY` | 10 покупок по карте за 2 минуты | 50 | Скользящее окно на sorted set в Redis, один Lua-скрипт |
| `IMPOSSIBLE_TRAVEL` | Покупка в Москве, через 15 минут — в Новосибирске | 60 | Последняя геопозиция карты в Redis, расстояние по формуле гаверсинуса, скорость больше 800 км/ч |
| `AMOUNT_ANOMALY` | Обычно тратит 2 000 ₽, а тут 150 000 ₽ | 40 | Среднее и дисперсия логарифма суммы по клиенту, алгоритм Уэлфорда в Lua; срабатывает от 3σ |
| `BLACKLISTED_CARD` | Скомпрометированная карта | 100 | Redis set |
| `BLACKLISTED_MERCHANT` | Подозрительный магазин | 60 | Redis set |
| `RISKY_CATEGORY_AT_NIGHT` | От 20 000 ₽ ночью на переводы, квази-кэш, азартные игры, ювелирку | 40 | Местное время продавца, MCC; состояния нет |

Баллы, параметры, включение правил и пороги хранятся в PostgreSQL и меняются через API без
перезапуска. Начальные значения задают миграции Flyway.

## REST API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/v1/decisions/{transactionId}` | Решение по операции со списком сработавших правил |
| `GET` | `/api/v1/decisions?cardId=&verdict=&limit=` | Последние решения с фильтрами |
| `GET` | `/api/v1/rules` | Все правила с баллами и параметрами |
| `PUT` | `/api/v1/rules/{code}` | Изменить правило: `{"enabled": true, "score": 50, "parameters": {...}}` |
| `GET`, `PUT` | `/api/v1/scoring` | Пороги: `{"reviewThreshold": 40, "blockThreshold": 80}` |
| `GET` | `/api/v1/blacklist/{cards\|merchants}` | Содержимое чёрного списка |
| `POST` | `/api/v1/blacklist/{cards\|merchants}` | Добавить значения: `{"values": ["card-0000001"]}` |
| `DELETE` | `/api/v1/blacklist/{cards\|merchants}/{value}` | Убрать значение из списка |

Пример — сделать правило частоты строже:

```bash
curl -X PUT http://localhost:8080/api/v1/rules/VELOCITY -H "Content-Type: application/json" \
     -d '{"enabled": true, "score": 60, "parameters": {"threshold": 5, "windowSeconds": 60}}'
```

Неверные параметры отклоняются с ответом 400 в формате RFC 9457, где в `detail` указана
причина — например, `threshold must be at least 2` или неизвестное имя параметра.

## Инженерные решения

**Порядок событий.** Транзакции партиционируются по идентификатору карты, поэтому события одной
карты обрабатывает один поток потребителя строго по очереди.

**Повторная доставка.** Kafka доставляет сообщения «хотя бы один раз». Защита устроена в два уровня:

1. Если по транзакции уже есть решение в PostgreSQL, она не оценивается заново: сохранённое
   решение публикуется ещё раз без изменений. Правила с состоянием её второй раз не видят.
2. Если сервис упал после обновления состояния в Redis, но до записи решения, транзакция будет
   оценена повторно. На этот случай каждый Lua-скрипт идемпотентен по `transactionId`: окно
   частоты использует его как элемент множества, а скрипты геопозиции и статистики сумм помнят
   последнюю транзакцию и отвечают на её повтор так же, как в первый раз.

**Атомарность в Redis.** Каждое правило с состоянием читает и обновляет его одним Lua-скриптом —
это одно атомарное обращение вместо нескольких команд.

**Время события, а не время обработки.** Окна и скорости считаются от момента покупки. Если сервис
отстал и разбирает накопившуюся очередь, результат правил не меняется. Опоздавшее событие не
сдвигает последнюю известную геопозицию карты назад во времени.

**Местное время.** Транзакция несёт часовой пояс продавца, как поле местного времени операции в
ISO 8583. Три часа ночи во Владивостоке — это восемь вечера в Москве.

**Аномальная сумма в логарифмах.** Суммы покупок распределены примерно логнормально. В обычной
шкале одна покупка в ювелирном растянула бы дисперсию так, что аномалий больше не нашлось бы.
В логарифмах правило отвечает на вопрос «во сколько раз больше обычного».

**Настройки без перезапуска.** Сервис держит в памяти неизменяемый снимок настроек и подменяет его
атомарно. Транзакция оценивается по одному снимку от начала до конца. Изменение через API
применяется сразу, остальные экземпляры подхватывают его при периодическом перечитывании (5 с).
Опечатка в имени параметра — ошибка, а не тихое значение по умолчанию.

**Отказ Redis.** Каждый вызов Redis на пути оценки идёт через circuit breaker (Resilience4j).
Когда Redis не отвечает, breaker после нескольких неудачных вызовов открывается, и дальше вызовы
отклоняются мгновенно, без ожидания таймаута. Клиент Lettuce при разрыве соединения тоже отказывает
сразу, а не копит команды. Правила, которым нужен Redis, пропускаются; правило рискованной
категории продолжает работать. Решение получает отметку `DEGRADED` со списком пропущенных правил.

Какой вердикт ставить без части правил — вопрос компромисса:

| Стратегия | Плюсы | Минусы |
|---|---|---|
| fail-open (`ALLOW`) | Клиенты ничего не замечают | Пока Redis лежит, пропускается всё, что ловят только правила с состоянием, включая украденные карты из чёрного списка |
| fail-closed (`BLOCK`) | Мошенничество не проходит | Никто не может заплатить: отказ Redis превращается в отказ банка |
| `REVIEW` от суммы | Потери ограничены, платежи продолжаются | Лишние подтверждения у клиентов, пока длится сбой |

По умолчанию выбран третий вариант: покупки от 5 000 ₽ уходят на подтверждение в приложении,
меньшие решаются оставшимися правилами. Подтверждение — привычное для клиента действие, а мелкие
суммы не стоят того, чтобы беспокоить всех. Стратегия и порог задаются в `application.properties`
(`antifraud.degradation.*`).

**Отказ PostgreSQL или Kafka.** Решение без записи в базу не публикуется, а запись без решения не
теряется: обработка повторяется с растущей паузой, пока зависимость не вернётся. Партиция ждёт,
и отставание потребителя видно в метриках. Сообщение, которое нельзя разобрать, пропускается
сразу, чтобы не останавливать партицию.

**Объяснимость.** Решение хранит список сработавших правил с баллами и текстом причины, например
`Moscow and Novosibirsk are 2811 km apart, purchases 15 min apart: 11244 km/h, faster than 800 km/h`.

**Разметка отдельно от транзакций.** Признак мошенничества идёт в отдельный топик: сервис его не
видит, как и настоящий банк узнаёт о мошенничестве позже, из претензий клиентов.

## Сценарии генератора

| Сценарий | Что происходит | Какое правило должно поймать |
|---|---|---|
| `VELOCITY_BURST` | 12–20 мелких покупок по карте за 2 минуты | `VELOCITY` |
| `COMPROMISED_CARD` | Покупка украденной картой | `BLACKLISTED_CARD` |
| `FRAUD_MERCHANT` | Оплата в магазине мошенников | `BLACKLISTED_MERCHANT` |
| `CLONED_CARD_TRAVEL` | Владелец платит дома, через 5–30 минут клон карты — за 1 500+ км | `IMPOSSIBLE_TRAVEL` |
| `ACCOUNT_TAKEOVER` | Электроника или ювелирка в 50–150 раз дороже обычного чека | `AMOUNT_ANOMALY` |
| `NIGHT_CASH_OUT` | 20–80 тыс. ₽ ночью по местному времени на переводы, квази-кэш, азартные игры | `RISKY_CATEGORY_AT_NIGHT` |
